一、链路体检明细

#层检查项状态证据影响
L1 算力入口 媒体算力入口是否先建 proposed 确认任务 断 runtime.route.ts:- createTask(..., true) 只建卡不执行 入口不建卡，创作者就没有授权机会，算力会被直接触发。
L2 HTTP 入口 执行口是否校验任务状态、裸入口是否停用（防绕过） 断 runtime.route.ts:- 状态校验；旧裸 /render-images 返回 410 没有状态校验或旧裸入口还在，就能跳过确认卡直接烧算力。
L3 确认后执行 confirmTask 放行后是否真实驱动渲染并闭环任务状态 断 runtime.route.ts:- → batchRenderGameImages → setStatus(succeeded/failed) 确认只改状态不执行，门禁就成了状态孤岛。
L4 渲染服务 batchRenderGameImages 是否只被受控入口调用 断 server/src 内调用方 = [无] 多一个调用方就多一条绕过确认卡的暗道。
L5 确认门禁 proposed → running 状态机本身可用 通 本测试实跑 TaskStore.createTask(true) + ConfirmationGate.confirmTask，断言通过 门禁机制自身可用，现由入口层复用，无需在工具内部重复声明。
L6 HTTP 入口 /api/tasks/:id/confirm|reject 路由是否挂载 通 app.ts:30 已挂载，tasks.route.ts:8 已实现 后端接口齐备，缺的是前端调用方。
L7 前端网关 client/lib/api.ts 是否封装提案与确认/拒绝接口 断 client/src/lib/api.ts 已补 proposeRenderImages / confirmRenderImages / rejectTask（走 /api/tasks/:id/reject） 前端没有这几个封装，确认卡就点不动后端门禁。
L8 ConfirmUI 卡片 ProposalCard / 座舱是否支持媒体类行动提案 断 ProposalCard.tsx 动作标签 = [propose_stage, start_pipeline, resume_task, approve_stage, modify_asset, render_images, propose_stage, start_pipeline, resume_task, approve_stage, modify_asset, build_text_game, render_images]；TextGameCockpit.tsx 已渲染 render_images 确认卡 卡片不认媒体 action，媒体渲染就不在人在回路体系内。
L9 算力工具 videoGenerateTool（i2v 工作流）是否有生产消费方 断 暂缓 server/src 内除定义文件与总装导出外，引用数 = 0（仅测试文件引用） 按约定暂缓：当前流水线只编译影视化切片清单，尚无视频工序；comfyui_i2v.json 模板已就绪，待新开视频工序时接入。
L10 前后端契约 action 枚举对齐 + chat_only 不出卡 + 未知意图不立项 断 后端 = [modify_asset, resume_task, approve_stage, propose_stage, start_pipeline, chat_only]；卡片标签 = [propose_stage, start_pipeline, resume_task, approve_stage, modify_asset, render_images, propose_stage, start_pipeline, resume_task, approve_stage, modify_asset, build_text_game, render_images]；App 分支 = [resume_task, build_text_game, approve_stage]；chat_only 过滤=false；无兜底立项=true 枚举错位或 chat_only 出卡时，未识别意图会落进 else 兜底重复立项（409）；现在未知意图只提示不执行。
